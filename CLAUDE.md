# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

The **Scheme Performance & Impact Calculator and Planner** — a pan-India dealer rebate dashboard, simulator and planner for Acme Paints.

It computes dealer-level **credit note (CN) liability** against slab-based rebate schemes, lets a user edit the scheme structure, and shows the effect on CN immediately. On a settled month it reports every scheme, every dealer, the business GSR, the CN and the blended payout rate (CN ÷ GSR).

**This is a sanitised public copy.** Client, product and scheme names and all business figures are replaced with made-up values; no client data is included.

## Capacity guards (review of 5 Nov 2026)

- **At most 2 edited frames are built at once** (`live.HEAVY`, a `BuildGate` in `app/core/cache.py`; each frame is ~0.11 GB). A request that waits 90 s for a slot gets 503 "The server is busy..." with `Retry-After`. The gate is re-entrant per thread; keep a gated block free of other cache calls where you can (build the input first, then gate the build).
- **Filter values are checked** against the live month (`live.scope_of`; 422 with a sentence otherwise). Every filtered view is cached by its filters, so made-up values used to add entries and push out the warm ones. Use `live.scope_of(...)`, never `req.scope()` / `scope_key` directly, in a route.
- **All India is never evicted** from `all_slabs_cached` (`memo(..., keep=)`); `maxsize` counts it.
- `/all-slabs/adjusted` copies only what it changes from the cached view (no deep copy); copy a row dict before changing it.
- **Login** (`app/auth.py`): failed logins are limited per address (5 / 15 min) and per username (10 / 15 min); Log out revokes the session on the server (in memory: a restart forgets it); `ADMIN_PASSWORD` must be a hash on uat and prod (`python -m app.auth_user admin ADMIN` prints one). Logins, dealer lists, moved dealers and version saves / archives / deletes are written to the `app.audit` log (who, what, when; never dealer data), and to `spi.audit_log` in the database.
- **Read-only queries are POSTs on purpose** (`/months`, `/months/next`, `/all-slabs/adjusted`, `/simulate-slabs` ...): the edits travel in the body, which can be MBs. Do not turn them into GETs.

## Startup cost — read this before debugging "no data"

Cold start is roughly **60 seconds** (~14s dealer frame, ~47s All-India slab build), and the `/trend` cache takes **several minutes** on top. A daemon thread warms both at startup. During that window the UI shows "—" and `/all-slabs` requests wait — **this looks broken and is not.** Each cache is built once per key (`app/core/cache.py`): requests for the same key wait for that one build instead of each starting their own, and a reload (`cache_clear`) never stores a build begun on the old frame. `GET /health` says `ready` once the dealer frame and the All-India slabs are built. Once warm, `/all-slabs` answers in ~0.3s and `/trend` in ~0.4s.

Do not restart the backend casually; you pay the whole warm-up again.

**Edits re-slab only what they change** (4 Nov 2026). `live.changed_pairs` compares the edited frame with the unedited one and lists the (scheme, component) pairs whose rows moved (a scheme edit also moves Value and Early Bird, which follow the dealer's total; `total_gsr` is ignored, no slab reads it). The other components come from caches of the unedited month (`served_component_records` for `/all-slabs/adjusted`, `_served_plan_components` for next month), equal to a full recompute (data tests in `backend/tests/test_engine_data.py`). `aggregate_bands` runs in numpy on integer group ids; `dealer_factors` caches the frame's product figures. Warm, an edit costs ~0.2-0.7 s per endpoint (was 1.2-2.8 s). Add any new cache to the `cache_clear` list in `reload_live`.

## Live data: daily sync from GCS

The live month (dashboard and simulator) comes from GCS, not a fixed file. `app/ingest/gcs_sync.py` (`python -m app.ingest.gcs_sync [--year Y --month M]`, run from `backend/`) lists the files directly in `gs://example-scheme-files/scheme-extracts/output/<YYYY>/<MM>/`, takes only `..._v<N>_no_condonation.xlsx`, and of those the newest upload date, then the highest `v<N>`. The names carry no date, so the upload date (IST) is the extract date. **Never read the `daily/` subfolder**: not every extract is copied there (October's stops at v15 / 15 Oct while the month folder has v20 / 28 Oct). It downloads that file to `backend/data/gcs/<YYYY>/<MM>/`, parses it once so the parquet cache is ready, then writes `latest.json`. `months.live_month()` serves the newest month with a `latest.json`. Superseded downloads are removed, and months older than the current one plus the last 3 (`LOADER_RETENTION_MONTHS=4`); GCS keeps every file.

In Docker the loader container runs the sync and the API's file watch swaps the file in. Without the loader (a single process, as before) the API runs that sync itself, as an earlier internal service did: `app/scheduler.py` starts it in a child process at start-up and daily at `LOADER_DAILY_AT` (14:00 IST; the files land ~13:00-13:15 IST), retries on failure (a failed Postgres load too: the sync then exits 2, the files are swapped in and the run is tried again), and calls `app.service.live.reload_live()` to swap the new file in without a restart. On by default except `APP_ENV=local`.

Settings come from `backend/.env.<APP_ENV>` (`app/config.py`); `backend/.env.example` lists every key. GCS access uses a read-only service account (`GCS_CREDENTIALS_JSON`, base64 of the key). `LIVE_MONTH` pins a registered label instead (e.g. `2026-09-d25`).

**Two file series share the folder and the name pattern** (from October 2026): the main CN extract and a gift / contest file (Shine On Gift, Glossa Gift, Wallpaper Roll, 5% Nova Prime ...; no business GSR, none of the CN schemes). Their versions interleave (Oct: main v20, v22; gifts v21, v23, v24), so "newest file" alone once loaded a gift file as October. The sync classifies each file by its header (`classify`: main = it has the business GSR columns; a ranged read, cached per generation in `kinds.json`) and keeps the newest of each kind: main in `latest.json`, gifts in `gifts.json`. A gift file never replaces the main one.

**Gifts are kept apart from CN** (user's decision, 2 Nov 2026): `app/ingest/gifts.py` parses the gift file into its own table, `app/core/gifts.py` + `GET /gifts` give dealers, qualified dealers, gifts earned, volume and GSR per scheme for the previous and current month, and `GiftsView.tsx` shows them under the month table. Nothing from it enters the dealer frame, the slab engine or any CN total. In a gift scheme "Clear Cut" is the number of gifts (for example 1 per 20 L) and "CN%" is 1 once qualified; Shine On's 1/2 looks like a tier, not a count (confirm with the client). 5% Nova Prime is rupees (Clear Cut = 5% of GSR) and is shown in ₹, still outside CN. Gifts are stored in Postgres in their own tables (below). **Gift detail and what-ifs** (user's request, 3 Nov 2026): Scheme detail lists the gift schemes of the gift file's month (the live month's, else the previous; `POST /gifts/detail`, `GiftDetail.tsx`) with dealers by gifts earned and by region. `infer_rule` (`app/core/gifts.py`) offers a rule for editing only where it reproduces the file for ≥99% of dealers: for example Glossa 1 per 20 L, Vivid Look Shine 1 per 15 L, Ancillary Offer 1 per 10 L, 5% Nova Prime 5% of GSR (illustrative values); the rest are view only. An edit (litres per gift / % of GSR, and the scheme's volume) adds the rule's change to each dealer's file figure, so untouched = the file. Edits live in the browser only (not saved, not CN). Gift names in Overall Schemes open their card; ← goes back. Gifts (count) and Paid (₹) are separate columns.

The UI always shows which file a month comes from ("data as of 1 Nov 2026 · v22", `fmtAsOf`), in the header and on each month column. `reload_live` reloads when any month's main or gift file changes (`months.data_signature`), not only the live one, and rebuilds `/trend`.

A file's extract date is when it was produced, not the last day it covers: September's final files are dated 1-4 October. A file extracted after its month ended is treated as the complete month.

## Historical months live outside the repo

`app/core/months.py` registers six monthly files resolved from `Path.home() / "Downloads"` — **not** from `backend/data/`. Source spreadsheets and all `.parquet` caches are gitignored, so a fresh clone has no data until those files are present.

Parquet caches are written **next to the source file** (i.e. into `~/Downloads`), keyed as `{name}.{sha1[:10]}.v{CONFIG_VERSION}{suffix}.parquet`. Two consequences:

- Bumping `CONFIG_VERSION` (`app/ingest/parse_raw.py:29`, currently 15) invalidates every cache and forces a full multi-minute re-parse.
- The cache suffix includes the **scheme count** (`.s46`, `.s48`). Discovering more schemes silently orphans older caches, which then fall back to re-reading the source — and fail if it has since been deleted.

Missing months degrade gracefully. A registered month whose file is not on this machine is left out of `/trend` and listed under `excluded` ("Source file not available on this server"); complete months synced from GCS fill the gap, and the live part month is projected. A month that fails to parse returns a generic `error` and logs the detail server-side — never put an exception's text (it holds file paths) in a response. The Plan tab must render with zero or one month (it crashed the whole app on an empty list once).

The client sends next month's scheme letter as an email, with an in-bill spreadsheet and a new-product deck attached. These are client documents and are not in this public copy. Points to remember:

## Architecture

```
Excel/CSV export  →  ingest  →  tidy dealer frame  →  slab engine  →  FastAPI  →  React
```

**`app/ingest/` — layout detection, discovery, calibration.** The hard part of this codebase. Monthly exports arrive in several different layouts (three so far: September "grouped", August "working", July "uniform"), detected from the header rather than the filename because filenames are unreliable. `load_month.py` normalises all of them into one tidy schema.

Scheme definitions are **inferred from the data, not configured**. `discover_schemes.py` pattern-matches the 2-row header to find schemes; `calibrate.py` then determines each component's payout formula empirically by testing candidates against the file's own Clear Cut column, because column *names* lie (`VALUE FA CN%` holds a flat rupee amount, not a percentage).

**`app/core/slab_engine.py` — bucketing and re-bucketing.** Slab edges are recovered from the data: a dealer's `achievement + next_slab` lands exactly on the next edge, so the distinct values of that sum *are* the edges. Edges are always derived from the **whole country, never the filtered view** — a published slab table belongs to the scheme, not to the region being looked at. Adjacent bands paying the same rate in the current scope are merged, because regional rate cards differ and foreign edges would otherwise split one real slab in two.

**`app/core/` — the calculation layer.** `scope.py` is the single filter implementation (accepts a bare string or a list; every endpoint uses it). `growth.py` answers "what does X% more sales cost in CN" — deliberately *not* by scaling CN, since slabs are thresholds. `project.py` projects a part-month file to full-month, again not pro-rata. `simulate.py` applies edited rates. `trend.py` does month-on-month and slab migration.

**Backend layout:** `app/main.py` is the app only (lifespan, middleware, `/health`, routers); routes are in `app/routers` (`auth`, `slabs`, `months`, `saved_versions`), request bodies in `app/schemas.py`, and what they compute in `app/service` (`live.py`: the live month, its frames and every cache, read as `live.LIVE` because a reload replaces it; `saved_versions.py`; `trend.py`). The API's DB calls use a pool (`app.spi.connection()`); command-line jobs use `connect()`. A version save is ONE transaction (`store.save`: definition, live results and saved snapshots).

**Frontend** is React 19 + Vite, four tabs in `App.tsx` (Overview / Plan / Simulator / Scenarios), talking to `BASE_URL` in `src/api/client.ts` (`/api`). The tab and the filters are in the address bar (`hooks/useUrlState.ts`): a reload keeps them, Back moves between tabs. A request that a newer scope or edit replaces is cancelled (`AbortController`; `isAbort` errors are never shown). ## Dealer list, slab editing, export

- **Dealer list** (`POST /dealers`, `frontend/src/components/DealerList.tsx`): opened from a slab row's dealer count. For the table as served, `slab_engine.dealers_in_row` applies the same rules as `build_slabs`, so the list always equals the count (checked on every row of a live month in three scopes). For a table with moved boundaries the browser sends the layout and the list is re-derived with `assign_dealers`. It returns dealer codes and names (client data) a page at a time; the aggregate endpoints still carry none. ADMIN and SCHEME_MANAGER may list them, VIEWER not (Login and roles, above).
- **Slab ranges never start below 0** (user's rule, 4 Nov 2026). A per-dealer-target row shows its dealers' achievement range clipped at 0 (returns make achievement negative), and the rate tier ("rate ₹500/dealer", `fmtTarget` in `computeImpact.ts`) where that range is 0 – 0 (VALUE FA's flat amounts, "Other (unattributed)"); the row and its CN stay. The server clips `slab_lower` / `slab_upper` of target rows and the not-qualified row's start at 0 (`build_slabs`, `aggregate_bands`); dealer lists pick target rows by rate, so they do not change.
- **Next slab = achievement (GSR (Q), or volume (Q)) + shortfall.** The file's "Next Slab" column is the shortfall; the same sum recovers the slab edges.
- **Slab boundaries are editable in every scheme.** `assign_dealers` prices bands two ways: `rates` (one card for the scope, as before) or `sources` — each new band names the original band it comes from, and **each dealer keeps their own region's card**: a dealer still in the source band keeps exactly their rate; one who crossed into it gets the rate most of their region earns there (national where the region has none). The first band is open below 0 (returns make achievement negative). Unchanged boundaries therefore move ₹0 (checked on every component in three scopes). Per-dealer target components start as one band 0–∞ and get boundaries with "+". Rate edits travel as `rate_overrides` (band, rate, new rate). The browser derives the layout from every distinct boundary of the served rows (`layoutOf` in `App.tsx`) — not one row per band: served rows merge same-rate neighbours per rate, so they disagree. Since 3 Nov 2026 the browser always sends this `sources` form, never `rates` (older saved scenarios with `rates` still load): the old single-card `rates` table was built from the served rows and could drop a slab (Glossa Enamel in one region lost its 7% band). **Slab and rate edits are kept when the filters change** (user's choice, 3 Nov 2026), as a saved scenario carries them (`carryLayouts` in `App.tsx`): a rate edit then applies, in any scope, to the dealers in that band earning that old rate; a toast says so.
- **Export** (`POST /export`, `app/api/export.py`): the browser sends its rows (edits exist only there); the server adds month, as-of date and the scope's dealers / volume / GSR, builds Summary, Schemes and Slabs sheets, and keeps nothing. Slabs columns (user's choice, 12 Nov 2026): Scheme, Component, Applicable regions (every region name of the row, comma separated, from the row's `regions`), Slab (no "(achievement range)"), Rate type, Dealers, Volume, GSR, Current rate, New rate (whole numbers without a decimal point), Actual CN, Simulated CN, Impact, CN % of GSR, Edited.
- **Two users never see each other's edits.** Every edit lives in that user's browser; the API is stateless and its caches hold only results of the served month (pure functions of scheme and scope). Keep it that way: never cache anything keyed by a user's edit. The one exception is a scenario the user chooses to **save** (below): it is shared on purpose.

## Domain invariants

These are load-bearing. Breaking one produces plausible-looking wrong numbers rather than an error.

- **CN = `cn_units` × rate.** `cn_units` is derived from the published payout (clear cut ÷ the rate that earned it), so an untouched row always reproduces exactly what was settled. Never inherit an actual CN and scale it.
- **Slab basis and rate base are different columns** and are not interchangeable. Luxury's slab is decided in litres while its CN% applies to rupees; mixing them produces nonsense boundaries.
- **GSR = DPL × (1 − in-bill %).** In-bill is the invoice discount off the dealer price list. It is not a CN scheme, but changing it changes GSR, and so the rate base of every % CN and the slab of every rupee-slabbed scheme. Litre/kg-slabbed schemes keep their slab. The extract's GSR is already net of the month's in-bill, so a new in-bill is applied as `GSR × (1 − new) / (1 − old)` per product × region, with volume held fixed.
- **GSR is de-duplicated per dealer.** Business GSR is `GSR(B) Value` + `GSR(B) Value %` + `GSR(B) TMBR Value Slab`, counted once per dealer (`TOTAL_GSR_METRICS`, `app/ingest/discover_schemes.py`). Value has two columns, normal and %, and each dealer carries exactly one. **Do not use the EB full-month GSR**: South runs no EB full-month scheme, so that column is empty for every South dealer (a large share of the book went missing). Per-scheme GSR is never summed across schemes — the same sale appears under several.
- **Within a scheme, each distinct source column counts once.** Components reading the same column collapse; components reading different columns accumulate. Except add-ons (4 Nov 2026): in a scheme with a GSR column, a component with no GSR column of its own ("Per 50 L", "Per 100 L", "Addn ...", Primer FA) pays on litres already in the main column, so its rows carry `vol_src` −1 and no total counts them (for Luxury this roughly halved the litres, to the file's own total).
- **A partial month is not a small month.** September is a mid-month snapshot carrying ~⅓ of a full month's payout. Anything that trends or forecasts must use `complete_months()`.
- **A settled month's credit notes are disbursed and non-recoverable.** Any simulated reduction is the cost of a *future* structure, never a saving. The UI must never imply otherwise.
- **Simulations hold dealer volumes fixed.** The true cost of a rate increase is therefore somewhat higher than shown, and this must be stated on screen rather than only in documentation.

Reconciliation runs within a couple of percent overall against the source file; only a few dormant schemes do not reconcile.

## Project status

The build in this repo predates requirements document **v1.0.1**, which specifies a substantially different product. Known divergences, confirmed with the user:

- v1.0.1 requires scheme definitions to come from **structured configuration entered each period**, explicitly not inferred. **The inference-based ingest layer stays unchanged for now** — do not rebuild `discover_*` / `calibrate` toward a config store until the GCS and DB schemas have been mapped.
- v1.0.1 adds a **product dimension** (category, mix share, realization value) that does not exist in the current data model, and **product mix as an editable lever** on GSR.
- Of seven scheme archetypes, the engine covers roughly three. Threshold Value CN, First-Occurrence CN, overlapping qualifying periods and the gift/contest layer are absent. The last three need transaction-level dated data the current monthly aggregate does not carry.
- The target UI is **one surface with three stacked, self-contained sections** (previous locked, current and next both editable), not the current three tabs. Each section carries its own full band/slab structure; slab rows are deliberately *not* aligned across periods, because editing a boundary makes side-by-side band comparison misleading.
- Nothing is persisted by default. An Excel export and a saved scenario (Scenarios tab) are the only artefacts a session produces.
